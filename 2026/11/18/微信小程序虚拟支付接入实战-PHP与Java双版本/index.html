微信小程序虚拟支付接入实战：签名、发货与那些踩过的坑（PHP / Java 双版本）

发表于2026-11-18|更新于2026-11-18|后端开发实战总结
|浏览量:

小程序里卖虚拟商品（会员、代币、课程、点数）和卖实物是两套完全不同的体系。实物走 wx.requestPayment，虚拟商品走微信虚拟支付（俗称道具直购 / 代币支付），而且iOS 端不允许在应用内直接完成虚拟支付。

这篇把接入流程、签名规则、发货回调，以及 PHP / Java 两套后端实现写清楚，坑放在最后。

一、先搞清楚能力边界

项目 说明
适用端 仅 Android。iOS 端不允许虚拟支付，只能在 UI 上隐藏入口或引导到 H5/客服
主体要求 企业/个体工商户，需在「小程序后台 → 功能 → 虚拟支付」申请开通
核心凭证 offerId（老文档叫 mid）、AppKey、沙箱 AppKey
前端 API wx.requestVirtualPayment（基础库 2.19.2+）

一句话记住：金额、余额、发货全部由服务端说了算，前端只负责拉起支付框。

二、端上如何判断

不要在前端 success 里直接加币，必须等发货回调。

三、签名规则（最容易错的地方）

虚拟支付有两个签名，用两把不同的 key，混用是最常见的 401：

  1. paySig —— 下单/拉起支付用，用 AppKey（沙箱用沙箱 key）做 HMAC-SHA256
  2. signature —— 调用 OpenAPI（查询余额、扣币、发货）用，用 access_token 体系 + 用户 SessionKey

待签串格式：POST\n/appid/path\n时间戳\n随机串\nbody，再做 HMAC-SHA256 后 hex 小写。

五、发货回调（这是唯一可信来源）

微信支付成功后会 POST 到你在后台配置的发货推送地址：

处理要点：

  1. 验签 + 解密：用 signature 规则校验，业务字段在加密块里，别直接读明文
  2. 幂等：同一个 OutTradeNo 可能推多次，按订单号加唯一索引
  3. 5 秒内返回成功，超时会重试；耗时逻辑丢队列，先回 {"ErrCode":0,"ErrMsg":"OK"}
  4. 主动补偿：定时任务拿本地待发货订单去 xpay/query_order 对账，别指望推送 100% 到达

六、常见问题清单

现象 原因 处理
前端拉起失败 -1 signData 不是原样字符串下发，被 JSON 再包了一层 下发原字符串，别二次序列化
401 / 签名错误 paySig 用了 SessionKey，或 signature 用了 AppKey 两把 key 分清
沙箱能付、正式 400 env 字段与实际 key 不匹配 沙箱 key 配 env=1
金额差了 100 倍 单位是分，不是元 price 传分
iOS 能点充值 没按 platform 隐藏入口 iOS 直接隐藏
重复加币 没做幂等 订单号唯一索引
发货丢了 依赖前端 success / 回调超时 定时对账 + 队列重试
账号被封 把虚拟商品包装成实物卖 老老实实走虚拟支付

七、上线前自检

  • iOS 端入口已隐藏（含二级页面、活动弹窗）
  • price 全部以分为单位，前端展示再除以 100
  • 订单号生成规则可回溯（时间 + 用户 id + 随机）
  • 发货回调验签、解密、幂等三件套齐了
  • 有对账任务：本地支付中订单 → 查询接口 → 补发或关单
  • 沙箱环境完整走通一遍（含取消支付、超时、重复回调）

写在最后

虚拟支付这块文档更新较快，字段名（mid / offerId）在不同版本里也换过。上线前一定要拿最新官方文档对一遍字段，尤其是 signature 的构造方式。

代码能跑，坑得自己踩一遍才记得住。
