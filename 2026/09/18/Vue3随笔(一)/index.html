Vue3 随笔（一）：把组件拆对，比写得多更重要

发表于2026-09-18|更新于2026-11-18|前端开发随笔
|浏览量:

后台项目做久了会发现，真正拖慢进度的不是不会写代码，而是组件拆错了。一个 800 行的 UserEdit.vue，谁都不敢动。

这篇记几条我自己踩出来的拆分经验，不是 API 手册。

一、按「变更原因」拆，不按「视觉区块」拆

最常见的错法是照着设计稿切：头部一块、表单一块、按钮一块。结果改一次业务规则，三个文件都要动。

判断标准是：这两部分会不会因为同一个原因被修改？

  • 会 → 放一起
  • 不会 → 拆开

比如「用户资料编辑」里，头像上传和字段表单看似都是 UI，但头像上传会因为存储方案变，字段表单会因为运营后台的字段配置变。它们应该分开。

二、容器组件只管数据，展示组件只管长相

好处很直接：展示组件能在 Storybook 里单独看，容器组件能单独测接口逻辑，不用为了看一眼样式先造一堆 mock。

三、v-model 别做成双向的万能口

一个组件同时接受 modelValue 又往外抛十几个事件，最后没人说得清谁改了数据。

父组件拿不到「为什么变了」，但这是对的——组件不应该知道业务为什么要改值。

四、provide/inject 是给「层级太深但仍属同一功能」用的

跨三层传一个 formContext 用 props 很痛苦，但拿 provide 当全局状态用更痛苦：改一次看不出影响范围。

我的判断：

场景 方案
父子直接传 props / emits
跨 2~3 层同功能 provide / inject
跨页面共享 Pinia
只是常量 单独模块 import

五、<script setup> 里别堆放一堆工具函数

超过 30 行就和业务逻辑分开，放 composables/useXxx.ts。理由不是「优雅」，而是：能单独测。

小结

  • 拆分看「变更原因」，不看像素
  • 容器管数据，展示管长相
  • v-model 只抛用户行为，别回写
  • 层级深才上 provide，跨页面用 Pinia
  • 逻辑超过 30 行就抽 composable
